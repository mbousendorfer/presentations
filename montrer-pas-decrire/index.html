Agorapulse · ProductI · Le geste
Le diagnostic

Sans contexte, il invente
une UI vraisemblable.

Un modèle de langage produit ce qui ressemble le plus à ce qu'il a lu. À défaut d'Agorapulse, il produit du SaaS générique — propre, crédible, et faux. Quatre symptômes reviennent toujours.

01

Des valeurs en dur

#4F46E5, padding: 12px, border-radius: 8px. Plausible partout, juste nulle part. Le jour où la palette bouge, rien ne suit.

02

Des composants réinventés

Une modale écrite à la main alors que le DS ship une Modale. Elle ressemble. Elle n'a ni les états, ni le focus, ni l'accessibilité.

03

Une grammaire étrangère

ap-button--primary au lieu de ap-button primary. Le double tiret vient d'ailleurs. Chez nous, les modifieurs sont plats.

04

Des couleurs hors de propos

Du bleu pour un bouton principal, du violet pour décorer. Chez nous ces couleurs veulent dire quelque chose — et pas ça.

La causeCe n'est pas un défaut du modèle. C'est un défaut de contexte. Et le contexte, ça se fournit.

Levier 01

Le mode plan : lire avant de lancer.

Comment y entrer
  • Dans l'IDE ou l'app : le sélecteur de mode passe de « Ask before edits » à « Plan mode »
  • Au clavier : Shift + Tab fait le tour des modes
  • Claude analyse, propose un plan, et n'écrit rien tant que vous n'avez pas dit oui

Vous relisez le plan comme vous reliriez une spec : est-ce qu'il a compris le problème, ou juste la phrase ?

Ce qu'on cherche dans le plan
  • Il a nommé les composants du DS qu'il compte utiliser
  • Il n'a pas prévu d'en inventer un qui existe déjà
  • Il a repéré les états : vide, chargement, erreur
  • Il pose les questions que vous n'aviez pas tranchées

Si le plan est vague, le résultat le sera. On corrige le plan, pas le code.

Le raccourci qui coûte cherSauter le plan, c'est passer trois fois plus de temps à rattraper l'écran après coup.

Agorapulse · ProductI · Le geste
La matière première

Un prompt utile a cinq parties.

Le vôtre peut être long. Il ne doit pas être vague. « Fais-moi un écran de filtres » et le squelette ci-dessous ne produisent pas le même objet.

Les cinq parties
  • L'intention — ce qu'on fabrique, en une phrase
  • Les garde-fous — ce qu'il ne doit pas faire
  • Le but — à quoi on saura que c'est réussi
  • Le procédé — dans quel ordre travailler
  • Les contraintes — le DS, la techno, le périmètre
Le squeletteà garder sous le coude
# intention Construis l'écran de [quoi] pour [qui]. # garde-fous Ne code rien avant que j'aie validé le plan. N'invente aucun composant : si le DS en a un, prends-le. # but Un designer doit pouvoir dire « oui, c'est ça » en 10 s. # procédé 1. Cherche les composants du DS par intention 2. Liste ce que tu comptes utiliser 3. Signale ce que je n'ai pas tranché 4. Attends mon feu vert # contraintes Design system Agorapulse, prototype HTML autonome. États vide / chargement / erreur inclus.

Un fichier texte à la racine de votre dossier, lu au démarrage de chaque session. Il évite de réexpliquer le décor à chaque fois. Court vaut mieux que complet — une page suffit.

« Dans ce projet… » ou « à chaque fois que… »

C'est le seul test dont vous avez besoin. Si la phrase commence par « dans ce projet », ça va dans CLAUDE.md. Si elle commence par « à chaque fois que je fais X », c'est un skill.

Levier 03

/design-guidelines

Le skill ne contient aucune donnée du design system. Il va la lire, à chaque fois, dans le repo agorapulse/design. C'est ce qui garantit qu'il ne vous sert jamais une valeur périmée.

CE QU'IL LIT

Les specs, en direct

Pour chaque composant : le sélecteur, les classes, les modifieurs réels, les tokens --comp-* avec leurs valeurs résolues, et un exemple.

CE QU'IL IMPOSE

Chercher avant d'écrire

Étape bloquante : trouver le composant existant par intention avant la première ligne. S'il couvre le besoin, on le prend tel quel.

CE QU'IL SAIT

Trois surfaces

html-prototype pour un fichier autonome, angular pour le vrai produit, figma pour des instances sur le canvas.

CE QU'IL EXIGE

Un accès au repo

gh authentifié, ou un clone local. Sans ça il vous le dira plutôt que d'inventer — c'est voulu.

Le seul geste à retenirLe déclencher au début du travail d'UI, jamais après. Après, c'est de la réparation.

La règle bloquante

On cherche par intention, pas par nom.

Le nom que vous avez en tête n'est presque jamais le nom du composant. Le skill traduit l'un vers l'autre — c'est une grande partie de sa valeur.

Ce que vous ditesCe que le DS shipPourquoi ce n'est pas anodin
un toastSnackbarUne recherche sur « toast » ne le trouve pas. Réécrit à la main, il perd sa chorégraphie d'apparition.
une bannière d'infoInfoboxQuatre types, une icône par type. Un rectangle coloré n'en est pas un.
un menu kebabAction DropdownLargeurs et espacements définis. Et pas de sous-menu en cascade chez nous.
une popupModaleGère le focus, l'échappement, l'empilement. Un div en position fixe, non.

Le vocabulaire

Trois étages. On prend le plus haut qui convient.

Vous n'aurez pas à les écrire vous-même — mais vous devez savoir les reconnaître, parce que c'est à ça qu'on voit qu'un écran est juste ou seulement joli.

1 --comp-* Propre à un composant --comp-button-height
--comp-badge-blue-background-color
2 --sys-* Une intention, un rôle --sys-color-border-color-default
--sys-text-style-*
3 --ref-* La primitive brute --ref-spacing-*, --ref-color-*
en dernier recours seulement

Sortir du dossier

Un écran qui ne s'ouvre pas ailleurs ne sert à rien.

Par défaut, le prototype va chercher les styles du design system sur le réseau. Pratique chez vous, fragile ailleurs. Dès que le fichier doit voyager — un ticket, un Slack, une pièce jointe — demandez-le autonome.

Pour travailler

Le fichier appelle les styles du DS en ligne. Léger, toujours à jour, se recharge tout seul quand le DS bouge.

La limite : sans réseau, ou dans un aperçu bridé, la page s'affiche nue.

Pour partager
Rends ce fichier autonome : tout le CSS du DS en ligne dans le fichier, aucun lien externe, aucun chemin absolu.

Le fichier grossit — c'est normal, et ça n'a aucune importance. Il s'ouvre partout, chez tout le monde.

Le testEnvoyez-vous le fichier par Slack et ouvrez-le depuis le téléchargement. S'il est nu, il n'était pas autonome.

Agorapulse · ProductIII · Le passage en Figma
Le discernement

Le HTML suffit plus souvent qu'on ne croit.

Figma n'est pas une étape supérieure. C'est un autre outil, avec un autre public. Choisissez selon qui va regarder, pas selon ce qui fait sérieux.

Restez en HTML si…
  • Vous illustrez une spec dans un ticket
  • Vous voulez qu'on clique pour comprendre
  • Vous testez un enchaînement, pas une mise en page
  • Le lecteur est un dev, un PM, un dirigeant

C'est le cas de la grande majorité de ce qu'un PM produit.

Passez en Figma si…
  • Un designer va reprendre et continuer le travail
  • Il faut poser l'écran à côté d'écrans existants
  • Le sujet est une question de mise en page, pas de flux
  • Ça alimente un fichier projet déjà en cours

Dans ce cas, prévenez le designer avant, pas après.

Le contresensPousser en Figma « pour faire propre » double le travail et crée un deuxième endroit à maintenir.

Agorapulse · ProductIII · à lire avant de toucher à Figma
Non négociable

Votre fichier. Le vôtre, et rien d'autre.

Contrairement au HTML, une erreur dans Figma peut abîmer le travail de quelqu'un d'autre — et l'API ne sait pas déplacer un nœud d'un fichier à l'autre pour réparer.

01

Un fichier bac à sable, à vous

Créez un fichier neuf, à votre nom. Jamais un fichier du design system. Jamais le fichier projet d'un designer.

02

On instancie, on ne dessine pas

Chaque élément doit être une instance du composant publié. Une frame dessinée qui ressemble à un bouton n'est pas un bouton.

03

On ne modifie jamais un composant du DS

Ni le master, ni la taille d'une instance. Une icône du DS garde sa taille native, toujours.

04

On annonce avant de ranger

Vider ou déplacer en masse, ça ressemble à une suppression. Dites où ça part avant, et où c'est arrivé après.

Si un composant manqueFaites-le dire explicitement, et signalez-le. Un élément fabriqué à la main ne doit jamais passer pour du DS.

Agorapulse · ProductIII · Le passage en Figma
Le piège le plus coûteux

Il existe un faux design system.
Il sort premier.

La recherche de composants dans Figma classe mal. Une bibliothèque miroir non canonique remonte avant les vraies — elle est crédible, et elle est fausse.

Les vraies
  • V2 Atoms — les composants de base
  • V2 Molecules — les composants composés
  • V2 Style Guide · Tokens — variables et styles de texte
  • Police Averta Std

Le skill sait les cibler. Il faut juste ne pas le contredire.

Le miroir à fuir
  • Archie UI Kit — non canonique
  • Autre police (Hanken Grotesk)
  • Ses propres tokens sémantiques

Un écran monté dessus a l'air juste et ne l'est pas. C'est le pire des cas : personne ne le voit avant le dev.

Le contrôleCliquez sur un composant posé : sa bibliothèque d'origine doit être une V2. Sinon, on recommence.

Les conventions maison

Un fichier se lit, il ne se raconte pas.

Si un designer doit reprendre votre fichier, ces quatre habitudes lui font gagner une demi-heure. Elles vous coûtent une phrase de plus dans le prompt.

01

Des sections côte à côte

Les explorations sur une même ligne, pas empilées. On les compare d'un balayage horizontal, sans scroller sur des milliers de pixels.

02

Un fond sombre sous les maquettes

Navy désaturé sur les sections : c'est ce qui fait ressortir des écrans blancs. Un fond blanc sur blanc ne montre rien.

03

Pas de cartes d'explication

Le board montre le design. Le raisonnement va dans la conversation ou dans la description du composant, pas sur le canvas.

04

Des composants, pas des copies

Dès le deuxième exemplaire d'un élément, on en fait un composant. Sinon chaque arbitrage est à réappliquer partout, à la main.

Et la couverture« Ajoute une Cover » veut dire instancier le composant Cover et le remplir. Jamais dessiner une couverture.

La ligne

Vous illustrez une intention.
Vous ne concevez pas le produit.

Cette ligne n'est pas une politesse. Un écran généré est convaincant bien avant d'être juste — et c'est exactement ce qui le rend dangereux quand il circule sans être annoncé pour ce qu'il est.

Allez-y
  • Illustrer un ticket
  • Comparer deux options
  • Trouver les trous de votre spec
  • Vérifier qu'un composant existe
Demandez d'abord
  • Toucher à un fichier Figma partagé
  • Un écran qui part à un client
  • Un parcours entier, pas un écran
  • Un composant qui n'existe pas encore
Passez la main
  • Trancher une question de conception
  • Ajouter au design system
  • Faire passer un proto pour une maquette validée
La phrase à coller à côté de chaque écran« Prototype fait par moi pour illustrer le ticket — pas une maquette validée. »

Quand ça ne marche pas

Six pannes, six gestes.

Le skill ne se déclenche pas
Le nommer : /design-guidelines. Vérifier le plugin avec /plugin.
« Je ne peux pas lire les specs »
gh auth status puis gh auth login. Vérifier l'accès à agorapulse/design.
Figma répond « rien de sélectionné »
Normal si le fichier est vide. Ça n'empêche pas de construire — continuez.
Le MCP Figma est déconnecté
/mcp → Figma → réauthentifier. Attention au bon compte Figma si vous en avez plusieurs.
Il répète la même erreur
/clear et repartir du fichier existant. Le contexte s'était encombré.
Le résultat est joli mais générique
Le skill n'a pas tourné. Recommencer en le nommant d'abord — ne pas rafistoler après.
En dernier recoursUn message d'erreur du skill est une bonne nouvelle : il refuse de deviner. C'est un silence poli qui devrait vous inquiéter.
